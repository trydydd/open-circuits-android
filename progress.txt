8. BUILDCONFIG IS DISABLED

9. CONFIGURATION CACHE IS ENABLED

13. SESSION-START: INSTALL THE ANDROID SDK BEFORE ANY GRADLE COMMAND
    The SDK is not pre-installed. Run this at the top of every new session
    before touching Gradle. Uses $HOME so it works regardless of user:

      SDK_DIR="$HOME/android-sdk"
      mkdir -p "$SDK_DIR/cmdline-tools"
      curl -fsSL -o /tmp/clt.zip \
        "https://dl.google.com/android/repository/commandlinetools-linux-11076708_latest.zip"
      unzip -q /tmp/clt.zip -d "$SDK_DIR/cmdline-tools"
      mv "$SDK_DIR/cmdline-tools/cmdline-tools" "$SDK_DIR/cmdline-tools/latest"
      export ANDROID_HOME="$SDK_DIR"
      yes | "$ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager" \
        "platforms;android-35" "build-tools;35.0.0"
      echo "sdk.dir=$ANDROID_HOME" > local.properties

    local.properties is gitignored and must be (re)created every session.
    export ANDROID_HOME before every ./gradlew invocation, or add it to
    the shell profile for the session. AGP also auto-downloads build-tools
    34.0.0 and platform-tools on first use — this is expected and fine.
    The cmdline-tools version (11076708) corresponds to SDK tools 12.0;
    check https://developer.android.com/studio if this URL ever 404s.

14. ROBOLECTRIC TESTS NEED isIncludeAndroidResources = true
    Without `testOptions { unitTests { isIncludeAndroidResources = true } }` in

    The WebViewClient.shouldInterceptRequest override returns an explicit

    asserts statusCode == 403 specifically.

20. ROBOLECTRIC SHADOWWEBVIEW HISTORY GOTCHA
    ShadowWebView.loadUrl() records the last URL but does NOT build the
    back/forward history that canGoBack() reads. To test back-navigation
    in Robolectric unit tests:
      - Use shadow.setCanGoBack(true) to set the precondition.
      - Use shadow.getGoBackInvocations() to assert goBack() was called.
      - setCanGoBack() is marked @Deprecated in Robolectric; suppress with
        @Suppress("DEPRECATION") at the call site.
    To actually populate history (e.g. for URL assertions after goBack),
    use shadow.pushEntryToHistory(url) instead of loadUrl().

21. UNIT TEST DEP: androidx.test:core IS NEEDED FOR ROBOLECTRIC + ACTIVITYSCENARIO
    ActivityScenario lives in androidx.test:core, not in robolectric itself.
    It must appear as testImplementation, not androidTestImplementation.
    Version 1.6.1 was added to libs.versions.toml as androidxTestCore and
    wired in app/build.gradle.kts.

22. BACK NAVIGATION USES OnBackPressedCallback, NOT onBackPressed() OVERRIDE
    The back-press handling is wired via
      onBackPressedDispatcher.addCallback(this, object : OnBackPressedCallback(true) { ... })
    This is the non-deprecated API for API 33+. In Robolectric tests,
    trigger it via activity.onBackPressedDispatcher.onBackPressed() — do NOT
    call activity.onBackPressed() directly (that chains through the dispatcher
    anyway but is itself deprecated on ComponentActivity).

23. WEBVIEW STATE SAVE/RESTORE PATTERN
    webView.saveState(outState) is called from onSaveInstanceState.
    In onCreate, if savedInstanceState != null, webView.restoreState() is called
    instead of loadUrl(). This means on rotation the page is restored from the
    bundle rather than reloaded from scratch. The Robolectric shadow's
    saveState/restoreState write/read the history index to the Bundle using
    internal keys "HISTORY" and "HISTORY_INDEX".

24. ESPRESSO TESTS REQUIRE REAL ASSETS — CANNOT RUN UNTIL CONTENT IS SYNCED
    WebViewBehaviorTest instrumented tests evaluate document.title and
    localStorage via evaluateJavascript. They need a real WebView rendering
    real HTML. Run `./scripts/sync_content.sh <tag>`, commit the assets, then
    run the instrumented tests on a device or emulator with airplane mode ON.

25. SYNC_CONTENT.SH SHA256 ENTRY FORMAT
    scripts/sync_content.sha256 uses the same two-space format as sha256sum:
      <64-hex-chars>  <tag>
    The 'test' entry uses an all-zero dummy hash so the SHA256 mismatch test
    (case 3) works offline. When pinning a real release, run:
      sha256sum /tmp/oc.tar.gz | sed "s|  .*|  <tag>|"

    anchored at end of line), so partial tag matches cannot collide.

30. ANDROID VECTORDRAWABLE HAS NO <circle> ELEMENT
    SVG's <circle> does not exist in Android's VectorDrawable format. The
    equivalent is a path of two semicircular arcs that form a closed loop:
      M{left},54 A{r},{r} 0 0,1 {right},54 A{r},{r} 0 0,1 {left},54 Z
    The common SVG trick of A r,r 0 1,0 x+0.001,y (near-complete arc) renders
    as a visible gap when stroked at large sizes. Two half-arcs are reliable.
    For a stroke-only ring: set fillColor="#00000000" and strokeColor/strokeWidth.
    For a filled circle: set fillColor and omit stroke. The Z (close path) is
    needed for fill to render correctly; without it, some renderers leave the
    path open and the fill bleeds.

31. SPLASHSCREEN THEME ATTRIBUTES TAKE NO NAMESPACE PREFIX
    When extending Theme.SplashScreen from core-splashscreen, the child theme
    attributes use NO namespace:
      <item name="windowSplashScreenBackground">...</item>   CORRECT
      <item name="android:windowSplashScreenBackground">...  WRONG for pre-31
      <item name="app:windowSplashScreenBackground">...      WRONG
    The library declares its own attrs (no namespace) in its res/values/attrs.xml
    and maps them to the platform android: attrs at runtime on API 31+. Using
    android: prefix directly fails silently on API 26-30 (minSdk = 26).
    postSplashScreenTheme (no prefix) is also a library attr, not a platform one.

32. TWO SEPARATE ic_launcher_foreground RESOURCES COEXIST
    R.mipmap.ic_launcher_foreground  — the PNG files in mipmap-*dpi/ folders
    R.drawable.ic_launcher_foreground — the vector XML in drawable/
    These are distinct resource types with distinct IDs. The adaptive icon XML
    and the splash theme reference @drawable/ic_launcher_foreground (the vector).
    ThemeTest.launcher_icon_present_at_all_densities checks R.mipmap.ic_launcher_foreground
    (the PNGs). Do NOT move the vector into mipmap-anydpi-v26/ — the anydpi
    qualifier beats all density qualifiers on API 26+, so the PNGs would be
    silently ignored for every real device, making the density test meaningless.

33. PURE PYTHON PNG GENERATION (no Pillow required)
    When rsvg-convert and ImageMagick are unavailable, valid RGBA PNGs can be
    written with only Python stdlib (struct + zlib). Key invariants:
      - Each scanline starts with a filter byte (0 = None/no filter)
      - Then 4 bytes per pixel: R G B A
      - Compress the raw bytes with zlib.compress()
      - IHDR chunk: struct.pack('>IIBBBBB', w, h, 8, 6, 0, 0, 0)
        bit depth=8, colour type=6 (RGBA), compression/filter/interlace=0
      - Each chunk: 4-byte length + 4-byte tag + data + 4-byte CRC32 of tag+data
      - CRC computed with zlib.crc32(tag + data) & 0xFFFFFFFF
    The generation script is not committed; see docs/icons-regen.md for
    the preferred rsvg-convert command when tooling is available.

34. ROBOLECTRIC DENSITY TESTING REQUIRES createConfigurationContext
    Changing context.resources.displayMetrics.densityDpi directly does NOT
    affect which mipmap bucket Robolectric selects; that field is read-only
    in the shadow. The correct pattern is:
      val cfg = Configuration(context.resources.configuration)
      cfg.densityDpi = DisplayMetrics.DENSITY_XHIGH
      val ctx = context.createConfigurationContext(cfg)
      val d = ctx.getDrawable(R.mipmap.ic_launcher_foreground)
    createConfigurationContext returns a new context whose resource resolver
    picks the right density bucket. Used in ThemeTest.launcher_icon_present_at_all_densities.

35. SPLASH BACKGROUND IS ALWAYS CREAM — NOT NIGHT-MODE AWARE
    themes.xml wires windowSplashScreenBackground to @color/brand_cream, which
    is a fixed #F6F3EB regardless of day/night mode. The values-night/colors.xml
    overrides @color/background to charcoal, but NOT brand_cream. Consequence:
    the splash screen is always cream-coloured, even in system dark mode.
    If a dark splash is wanted in future, change the themes.xml item to reference
    @color/background instead of @color/brand_cream. This was a deliberate choice
    to keep the splash visually consistent with the site's light-mode branding.

36. ic_launcher_background.xml MUST USE <shape>, NOT <drawable android:color>
    The background for an adaptive icon must be a Drawable resource. The correct
    form in drawable/ is a shape drawable:
      <shape><solid android:color="@color/brand_cream"/></shape>
    The alternative form <drawable android:color="..."/> is a ColorDrawable alias
    valid only as an inline resource reference, not as a standalone Drawable file.
    Referencing a plain @color/... directly in the adaptive-icon XML (without the
    shape wrapper) causes aapt to fail: "android:drawable attribute is not
    a Drawable resource."

GOTCHAS AND HANDOFF NOTES
--------------------------

37. JAVA PACKAGE SHADOWED INSIDE android {} DSL BLOCK
    The kotlin identifier `java` is shadowed inside the android {} block by AGP's
    java compile options extension. `java.util.Properties()` inside android {}
    resolves to "AGP java extension".util which fails. Fix: add
    `import java.util.Properties` at the top of the .kts file and load the
    properties file at the top level (before android {}), then reference the
    captured value inside the block.

38. ASSIGNING release SIGNING CONFIG IN buildTypes
    signingConfigs.getByName("debug") is always available (AGP creates it).
    When keystore.properties is absent (CI without secrets), fall back to debug
    signing so `assembleFossRelease` still succeeds. The release signingConfig
    block is left with null fields when the props file is absent; the buildTypes
    block selects debug vs release based on whether the file exists.

39. assertNoGms USES DECLARED DEPS, NOT RESOLVED CLASSPATH
    The assertNoGms task checks ExternalDependency.group in all configurations
    at configuration time rather than resolving classpaths at execution time.
    This is configuration-cache compatible (no Task.project access at execution time).
    Using FileCollection inputs with configurations caused variant ambiguity errors
    (multiple matched variants); resolved-at-configuration-time artifact scanning
    caused "Task.project accessed at execution time" warnings. Declared-dep
    checking is simpler, cache-safe, and sufficient because GMS would only enter
    via an explicit dependency, never transitively in this offline app.

40. FLAVOR-SPECIFIC CONFIGURATIONS ARE NAMED {flavor}{BuildType}CompileClasspath
    After adding productFlavors, AGP creates variant-specific configurations like
    fossDebugCompileClasspath, fossReleaseCompileClasspath, playDebugCompileClasspath,
    playReleaseCompileClasspath. These are not available until after AGP processes
    the android {} block. Accessing them in tasks.register {} before afterEvaluate
    works, but using them as FileCollection inputs triggers variant ambiguity errors.

41. notCompatibleWithConfigurationCache DISCARDS THE ENTIRE BUILD'S CACHE ENTRY
    `task.notCompatibleWithConfigurationCache(reason)` does not just skip caching
    for that one task; it causes the entire configuration cache entry for that
    WHOLE BUILD to be discarded. So if assertNoGms were run as part of `./gradlew
    check`, the cache for the entire check invocation would be thrown away and all
    93+ cache problems would be reported. Every subsequent `./gradlew check` run
    would be a cold start. This is why assertNoGms instead captures dependency
    groups at configuration time (no project access in doLast) — keeping the check
    invocation fully cache-compatible.

42. PASSING CONFIGURATION-TIME DATA TO doLast WITHOUT ACCESSING project
    Inside `tasks.register("foo") { ... }`, the lambda body is a configuration-time
    action and can access `project` freely. `doLast { ... }` is execution-time and
    must NOT access `project` when the configuration cache is enabled. The idiomatic
    Gradle pattern to bridge the two:
      val data: SomeType = computeAtConfigurationTime()  // uses project.*
      inputs.property("myKey", data)
      doLast {
          val d = inputs.properties["myKey"] as SomeType  // safe: task.inputs, not project
      }
    For collections, `inputs.property` requires the value to be serializable (String,
    Int, List<String>, etc.). Complex objects must be reduced to primitives first.

43. flavorDimensions SYNTAX AND REQUIRED dimension ON EACH FLAVOR
    In Kotlin DSL, flavor dimensions must be appended with `+=`:
      flavorDimensions += "distribution"    // correct
      flavorDimensions = listOf(...)        // also works but verbose
    Each productFlavor block must explicitly set `dimension = "distribution"`.
    Omitting it causes: "All flavors must now belong to a named flavor dimension.
    Learn more at https://d.android.com/r/tools/flavorDimensions-missing-error-message.html"

44. BUILD OUTPUT PATHS AFTER ADDING FLAVORS
    APK:  app/build/outputs/apk/foss/release/app-foss-release.apk
    AAB:  app/build/outputs/bundle/playRelease/app-play-release.aab
    These paths are tested by the scripted cases (foss_apk_no_gms, play_aab_no_gms)
    and referenced in B9/B10 CI workflow tasks. The flavor name and build type appear
    as separate directory segments for APKs; for AABs the flavor+type are joined
    (playRelease). This asymmetry is AGP behaviour, not a project choice.

45. Properties().apply { load(...) } SHADOWING INSIDE android {} LAMBDAS
    Even after adding `import java.util.Properties`, calling
    `Properties().apply { load(file.inputStream()) }` inside the android {} block
    fails because `load` is resolved against the lambda receiver (an AGP DSL object),
    not `java.util.Properties`. The fix is `also { props -> props.load(...) }` (explicit
    receiver name), or simply load the properties before the android {} block at
    top-level scope. Top-level loading is cleaner and avoids all receiver shadowing.

GOTCHAS AND HANDOFF NOTES
--------------------------

46. AGP PKDS SIGNING BLOCK IS NON-DETERMINISTIC BY DESIGN
    AGP (8.7+) embeds a PKDS (0x504b4453) block in the APK signing block alongside
    the standard V2 signature (0x7109871a). The PKDS block ("dependency info") contains
    a random nonce per signing operation, making byte-level APK identity impossible
    even when the source, toolchain, and signing key are all identical. The V2 signature
    block itself IS deterministic (RSA-PKCS1-v1.5 with the debug key). The PKDS block
    lives outside the ZIP entries — unzip -lv CRC32 comparison is therefore unaffected.
    Content-level reproducibility (all extracted files identical) is what F-Droid verifies
    and what the verification script checks.

47. verify_reproducible.sh USES TWO CHECKS IN SEQUENCE
    (a) unzip -lv: compares CRC32, uncompressed size, and filename for every ZIP entry
        in the central directory. Fast, catches ordering and content mismatches.
    (b) sha256sum of extracted non-META-INF files: confirms byte-for-byte identity of
        every code/resource/asset file. Excludes META-INF/ (signature files), which are
        stripped by F-Droid before comparison. Together these two checks satisfy F-Droid's
        reproducibility definition without being blocked by the PKDS nonce issue.

48. AbstractArchiveTask SETTINGS DO NOT AFFECT AGP'S APK PACKAGER
    tasks.withType<AbstractArchiveTask>().configureEach { isPreserveFileTimestamps=false;
    isReproducibleFileOrder=true } fixes timestamps and ordering in Gradle's own Zip/Jar
    tasks (e.g. the lint-checks.jar). AGP's packageFossRelease task is a custom
    PackageAndroidArtifact task that does NOT extend AbstractArchiveTask. AGP controls
    its own ZIP timestamp handling internally; it already writes 1980-01-01 00:00 (the
    ZIP epoch) for all entries when building release APKs. The AbstractArchiveTask
    settings are still needed for any non-AGP archive tasks in the project (e.g. the
    :lint-checks:jar task).

49. GITHUB ACTIONS 'on' KEY IS YAML BOOLEAN TRUE
    PyYAML 5.x parses bare 'on' as the boolean True (YAML 1.1 spec). When the workflow
    YAML is verified with python -c "yaml.safe_load(...)", the 'on' key appears as
    Python's True, not the string 'on'. This is expected and does not affect GitHub
    Actions parsing (GitHub Actions uses its own YAML parser that handles 'on' as a
    keyword). Use d[True] or d.get(True) in Python scripts if you need to read the
    triggers programmatically.

50. PLAY STORE CHARACTER LIMITS ARE CONTENT CHARS, NOT BYTE COUNT
    The ledger test cases use `wc -c` which counts bytes (including the
    trailing newline). For ASCII-only metadata the byte count equals
    character count + 1 (for the newline). The limits in the tests are
    therefore +1 relative to the Play Store UI limit:
      title:             wc -c <= 31  (30 chars + newline)
      short_description: wc -c <= 81  (80 chars + newline)
      full_description:  wc -c <= 4001 (4000 chars + newline)
      changelogs:        wc -c <= 501 (500 chars + newline)
    If non-ASCII characters (multi-byte UTF-8) are ever introduced, wc -c
    will overcount. Switch to `wc -m` for character counting in that case.

GOTCHAS AND HANDOFF NOTES
--------------------------

55. SDK CACHE KEY INCLUDES GRADLE WRAPPER VERSION
    The Android SDK cache key incorporates gradle-wrapper.properties hash:
      key: android-sdk-${{ runner.os }}-${{ hashFiles('gradle/wrapper/gradle-wrapper.properties') }}
    This ensures cache invalidation if the wrapper version changes, avoiding
    version mismatches between Gradle and the SDK tools. The restore-keys
    fallback allows partial matches if the wrapper version changes.

56. SDK SETUP CHECKS IF ALREADY CACHED
    The sdkmanager installation step uses a conditional:
      if [ ! -f "$SDK_DIR/cmdline-tools/latest/bin/sdkmanager" ]; then
    This avoids re-downloading the 400+ MB cmdline-tools on every run when
    the cache is hit. Without this check, every run would download even with
    a valid cache (defeating the purpose of caching).

57. GITHUB ACTIONS ENVIRONMENT VARIABLES VIA $GITHUB_ENV
    The SDK setup step exports ANDROID_HOME to the workflow environment:
      echo "ANDROID_HOME=$SDK_DIR" >> "$GITHUB_ENV"
    This persists the variable for all subsequent steps in the job.
    Using `export ANDROID_HOME=...` in a run step only affects child processes
    within that step. The $GITHUB_ENV approach is the GitHub Actions idiom.

58. LINT AND TEST JOBS RUN SEQUENTIALLY, NOT IN PARALLEL
    The workflow has separate steps for lintFoss, lintPlay, testFoss, testPlay,
    etc., rather than combining them (e.g. ./gradlew :app:lintFoss :app:lintPlay).
    This provides better readability in the Actions UI and allows faster failure
    detection: if lintFoss fails, the user sees that immediately without waiting
    for Play lint. Gradle's local build cache (~/.gradle/caches/) is persistent
    across steps, so there is minimal redundant work.

59. UPLOAD-ARTIFACT USES if: always() TO CAPTURE FAILURES
    The artifact upload step has `if: always()`, ensuring artifacts are uploaded
    even if earlier steps fail. Without this, a failed lint or test would prevent
    APK/AAB artifact upload, making it harder to debug via the Actions UI.

60. BUILD AND RELEASE WORKFLOWS MUST NOT MODIFY MAIN
    The build workflow (B9) runs on pull_request and push to main, but it does
    not commit or push any changes. Contrast with the release workflow (B10),
    which will push APK/AAB artifacts to GitHub Releases. The build workflow is
    pure CI (verify code quality); the release workflow is deployment (push
    artifacts). Keeping them separate prevents accidental modification of main.
